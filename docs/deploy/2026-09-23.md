**`shared_infra` changed** (`8c74754`, `ddd180e`, `b93c277`). Every release statically embeds it, so
**all seven backend images must be rebuilt** — not just the services whose own app changed. That is
why the build step below names all of them.

Two ordering rules this deploy is bound by:

* **The migration goes first.** 129 and 130 add what the new code reads.
* **Gateway ships with-or-before auth, never auth alone.** Auth returns `:refresh_expired` and
  `:refresh_reused` as strings that `InternalApi.decode_result/2` rehydrates with
  `String.to_existing_atom/1`. A gateway that has not been rebuilt does not have those atoms, decodes
  them as raw strings, misses every clause, and answers **400 instead of 401** on refresh. The single
  `up -d` below satisfies this by bringing them up together.

The same wire applies to the implicit accept's `request_accepted` flag, but it degrades safely in both
directions (unknown atom → string → `nil` → no frame), so it does not constrain the order.

## 0. Pull, and confirm HEAD

```bash
cd ~/chat-platform
git fetch origin
git checkout main
git pull --ff-only origin main
```

**Shows it worked** — and records the commit every later step checks against. Run this in the **same
shell** you will use for the rest of the deploy:

```bash
export EXPECTED=$(git rev-parse --short HEAD)
echo "deploying: $EXPECTED"
git log --oneline -1
git status --porcelain
```

`$EXPECTED` is the single source of truth from here on — step 4 builds with it and step 5 asserts the
running containers report it, so nothing below hardcodes a SHA that can go stale.

`git status --porcelain` must print **nothing**. If it prints anything, stop: something on the box has
been edited by hand and `git pull --ff-only` may not have applied cleanly.

> **If you open a new shell** at any point, `$EXPECTED` is gone and the later checks become
> meaningless rather than failing loudly. Re-derive it before continuing:
> `cd ~/chat-platform && export EXPECTED=$(git rev-parse --short HEAD)`.

## 3. Migrations 129 and 130

Both are idempotent and both are byte-identical between the two locations they are written to. Apply
the release-bundled copies:

```bash
docker compose -f docker-compose.prod.yml exec -T postgres \
  psql -v ON_ERROR_STOP=1 -U chat_user -d chat_platform \
```

`ON_ERROR_STOP=1` matters: without it `psql` reports success after a failed statement.

**Shows it worked** — the columns and table the new code reads must now exist:

```bash
docker compose -f docker-compose.prod.yml exec -T postgres \
  psql -U chat_user -d chat_platform -c \

    WHERE table_name = 'fcm_tokens' AND column_name IN ('kind','environment')
```

Expect **three rows**: `kind`, `environment`, `deleted_at`. Fewer means a migration did not apply —
stop and read the `psql` output again.

## 5. Bring the backend up — gateway and auth together

One command, all seven. **Auth is never brought up alone** (see the atom note at the top), and the
`--profile kafka` flag is required or `notification` is not a known service:

```bash
docker compose -f docker-compose.prod.yml --profile kafka up -d \
  gateway auth conversation user message media notification
```

**Shows it worked** — all seven `Up`, and the API answering:

```bash
docker compose -f docker-compose.prod.yml --profile kafka ps \
  gateway auth conversation user message media notification \
  --format '{{.Service}}\t{{.Status}}'
curl -s -o /dev/null -w '%{http_code}\n' https://api.growblic.com/health
```

Expect seven `Up …` lines with no `Restarting`, and `200`.

**Then confirm every container is running THIS commit.** `GIT_SHA` is baked into each image as a
runtime env, so this is the check that catches a service you forgot to rebuild — the one failure mode
that otherwise looks completely healthy:

```bash
for s in gateway auth conversation user message media notification; do
  got=$(docker compose -f docker-compose.prod.yml --profile kafka exec -T "$s" sh -c 'echo $GIT_SHA' | tr -d '\r')
  if [ "$got" = "$EXPECTED" ]; then verdict=OK; else verdict="MISMATCH (expected $EXPECTED)"; fi
  printf '%-14s %-12s %s\n' "$s" "$got" "$verdict"
done
```

All seven must read **OK**. Any `MISMATCH` — an older SHA, or `unknown` — means that service did not
rebuild; go back to step 4 for it. This matters most for `gateway` and `auth`: a stale gateway is
exactly the 400-instead-of-401 failure described at the top.

If every row says `MISMATCH (expected )` with nothing after `expected`, `$EXPECTED` is unset — you are
in a different shell. Re-derive it as described in step 0 and run this check again; do not proceed on
an unverified stack.

**Then read the logs for a boot loop** — a release that crashes on a bad env restarts silently behind
`restart: unless-stopped` and `ps` can still say `Up`:

```bash
docker compose -f docker-compose.prod.yml --profile kafka logs --tail=40 \
  gateway auth conversation user message media notification | grep -iE "error|CRASH|Kernel pid" | head -20
```

No output is the pass. If `notification` complains about APNs, that is expected and harmless: the
sender stays disabled while `APNS_KEY_ID` / `APNS_TEAM_ID` / the key path are unset.

## 6. AASA — validate, then reload Caddy

**No recreate.** The AASA is served inline by a `respond` directive, not from a mounted file, so this
step is validate + reload and nothing else. Caddy keeps running throughout.

**Validate before reloading.** The Caddyfile is a live bind mount, so the container is already reading
the pulled file — `validate` checks exactly what a reload would apply, while the running server is
still serving the old config:

```bash
docker compose -f docker-compose.prod.yml exec -T caddy \
  caddy validate --config /etc/caddy/Caddyfile
```

Expect `Valid configuration`. **If it does not say that, stop here** and change nothing — the running
Caddy is unaffected and the site stays up.

```bash
docker compose -f docker-compose.prod.yml exec -T caddy \
  caddy reload --config /etc/caddy/Caddyfile
```

**Shows it worked** — and this is also live check 3. **Read the body, not just the status code:**

```bash
curl -sS -D- https://web.growblic.com/.well-known/apple-app-site-association \
  | grep -iE "^HTTP/|^content-type|^content-length|^location"
echo "--- body ---"
curl -sS https://web.growblic.com/.well-known/apple-app-site-association | python3 -m json.tool
```

All four must hold:

* `HTTP/2 200` — **not** 301 or 302. iOS does not follow redirects for this file.
* `content-type: application/json`. Without the `header Content-Type` line this is `text/plain` and
  iOS rejects the file.
* **`content-length: 118`, not 0.** This is the one that has actually bitten: an earlier `respond`
  here used a backtick-quoted body that did not survive Caddyfile parsing and served **200 with an
  empty body** — healthy-looking and completely broken. `caddy validate` does not catch it. The
  current directive is one line, double-quoted, inner quotes escaped, and was verified serving 118
  bytes against `caddy:2.8-alpine` before this deploy — but check it here anyway.
* `python3 -m json.tool` parses it and it contains `FXGBWKT8FB.com.growblic.exway` with `/call/*` and
  `/join/*`. If the body were empty, this command errors — which is the point of using it.

Confirm Android did not regress — it shares the site block, though not the handler:

```bash
curl -sS -o /dev/null -w '%{http_code} %{content_type} %{size_download}\n' \
  https://web.growblic.com/.well-known/assetlinks.json
```

Expect `200 application/json` and a non-zero size.

And confirm the site block as a whole is still fine, since a reload affects every host Caddy fronts:

```bash
for h in api.growblic.com web.growblic.com media.growblic.com; do
  printf '%-22s %s\n' "$h" "$(curl -s -o /dev/null -w '%{http_code}' https://$h/health 2>/dev/null || echo ERR)"
done
docker compose -f docker-compose.prod.yml ps caddy --format '{{.Service}}\t{{.Status}}'
```

Caddy must read `Up …`, **not** `Restarting` — a restart loop here takes api, web and media down
together.

> **Two things to know about the AASA.** It is served from **web.growblic.com** only, because
> `growblic.com` is a `redir` block and a redirect breaks universal links. The iOS app's Associated
> Domains entitlement must therefore read `applinks:web.growblic.com` — if it names the apex or
> `www`, the link silently falls back to Safari and nothing is logged server-side. And **`/join/*`
> has no web route yet** (`apps/web/src/app` has `call/[linkId]` and `invite/[code]`, no `join`): the
> path is claimed for the app, but a user without the app installed gets a 404 instead of a landing
> page. Worth a route in the web slice.

### 7.1 Demo login works

```bash
API=https://api.growblic.com

REQ=$(curl -sS -X POST $API/api/v1/auth/otp/request \
  -H 'content-type: application/json' \
  -d '{"phone_number":"+15550199001","purpose":"login"}')
echo "$REQ"
OTP_ID=$(echo "$REQ" | python3 -c 'import json,sys;print(json.load(sys.stdin)["otp_request_id"])')

LOGIN=$(curl -sS -X POST $API/api/v1/auth/otp/verify \
  -H 'content-type: application/json' \
  -d "{\"otp_request_id\":\"$OTP_ID\",\"phone_number\":\"+15550199001\",\"otp_code\":\"900001\",\"device_id\":\"deploy-check-2026-09-23\"}")
echo "$LOGIN"
```

**Shows it worked**: `$LOGIN` contains an `access_token` and a `refresh_token`. If the verify returns
`auth.otp_invalid`, the allowlist is not loaded — check `REVIEWER_TEST_LOGINS` is set in `.env` and
that `auth` was recreated in step 5.

### 7.2 The refresh grace window

The claim: replaying a **just-rotated** refresh token inside 30 s returns a fresh pair; outside it
returns `auth.refresh_reused`. Both halves on account A only.

```bash
R1=$(echo "$LOGIN" | python3 -c 'import json,sys;print(json.load(sys.stdin)["refresh_token"])')

# Rotate once. R1 is now the "just-rotated" token.
curl -sS -X POST $API/api/v1/auth/refresh -H 'content-type: application/json' \
  -d "{\"refresh_token\":\"$R1\"}" | head -c 200; echo

# INSIDE the window: replay R1 immediately.
echo "--- inside 30s, expect 200 + a token pair ---"
curl -sS -o /tmp/inside -w '%{http_code}\n' -X POST $API/api/v1/auth/refresh \
  -H 'content-type: application/json' -d "{\"refresh_token\":\"$R1\"}"
head -c 200 /tmp/inside; echo
```

Expect **200** and a body with `access_token`.

```bash
# OUTSIDE the window: same token, after the 30s grace has passed.
sleep 35
echo "--- outside 30s, expect 401 auth.refresh_reused ---"
curl -sS -o /tmp/outside -w '%{http_code}\n' -X POST $API/api/v1/auth/refresh \
  -H 'content-type: application/json' -d "{\"refresh_token\":\"$R1\"}"
cat /tmp/outside; echo
```

Expect **401** and `"code":"auth.refresh_reused"`.

A **400** here rather than a 401 is the exact gateway/auth atom mismatch described at the top — it
means the gateway image was not rebuilt. Re-run step 4 and step 5 for `gateway`.

> **Account deletion is deliberately not checked here.** It is only ever exercised against a throwaway
> account created for the purpose, never against a reviewer or a real account. Do it separately.

## Rollback

The dump from step 2 is the only thing that undoes the migrations. Roll back in the reverse order of
the deploy.

**Code only** (the common case — the new images misbehave but the schema is fine). Both 129 and 130
are additive, so the previous images run happily against the new schema:

```bash
cd ~/chat-platform
git log --oneline -12                       # pick the last known-good SHA
git checkout <LAST_GOOD_SHA>
export GIT_SHA=$(git rev-parse --short HEAD)   # deliberately re-derived: this is the ROLLBACK commit, not $EXPECTED
docker compose -f docker-compose.prod.yml --profile kafka build \
  gateway auth conversation user message media notification
docker compose -f docker-compose.prod.yml --profile kafka up -d \
  gateway auth conversation user message media notification
curl -s -o /dev/null -w '%{http_code}\n' https://api.growblic.com/health
```

**Caddy only** (the AASA is wrong, or the site misbehaves after step 6). Validate + reload, same as
the deploy — the Caddyfile is a live bind mount, so restoring the file and reloading is the whole
rollback. No recreate:

```bash
git checkout <LAST_GOOD_SHA> -- infra/caddy/Caddyfile
docker compose -f docker-compose.prod.yml exec -T caddy \
  caddy validate --config /etc/caddy/Caddyfile
docker compose -f docker-compose.prod.yml exec -T caddy \
  caddy reload --config /etc/caddy/Caddyfile
curl -s -o /dev/null -w '%{http_code}\n' https://api.growblic.com/health
docker compose -f docker-compose.prod.yml ps caddy --format '{{.Service}}\t{{.Status}}'
```

If Caddy is already **restart-looping** it cannot be `exec`-ed into, so `reload` will not work. Restore
the file and let the restart policy pick it up:

```bash
git checkout <LAST_GOOD_SHA> -- infra/caddy/Caddyfile
docker compose -f docker-compose.prod.yml restart caddy
docker compose -f docker-compose.prod.yml logs --tail=30 caddy
```

**Full restore, including the schema** — last resort. This **destroys every row written since the
dump**, so take a second dump of the current state first or you lose the evidence of what went wrong:

```bash
docker compose -f docker-compose.prod.yml exec -T postgres \
  pg_dump -U chat_user -d chat_platform --no-owner --no-acl \
  | gzip -9 > ~/failed-state-2026-09-23.sql.gz

docker compose -f docker-compose.prod.yml --profile kafka stop \
  gateway auth conversation user message media notification

docker compose -f docker-compose.prod.yml exec -T postgres \
  psql -U chat_user -d postgres -c \
  "DROP DATABASE chat_platform WITH (FORCE); CREATE DATABASE chat_platform OWNER chat_user;"

gunzip -c ~/predeploy-2026-09-23.sql.gz | \
  docker compose -f docker-compose.prod.yml exec -T postgres \
  psql -v ON_ERROR_STOP=1 -U chat_user -d chat_platform

# then the code rollback above
```

**Shows the restore worked** — the 130 column is gone again, so you are genuinely on the old schema:

```bash
docker compose -f docker-compose.prod.yml exec -T postgres \
  psql -U chat_user -d chat_platform -c \
  "SELECT count(*) FROM information_schema.columns
    WHERE table_name = 'users_auth' AND column_name = 'deleted_at';"
```

Expect `0`.

## Still blocked after this deploy

* **APNs is live-untested.** The sender stays disabled while `APNS_KEY_ID`, `APNS_TEAM_ID` and the
  `.p8` path are unset. The `.p8` lives **only on the server as a secret, never in git**. When the key
  exists, set the three and `up -d auth notification`, then check a dummy token returns
  `BadDeviceToken` — that proves the provider JWT signs and Apple accepts it.
* **`apps/web` has no message-requests bucket.** Accept/Decline exist on Android and iOS only. The
  implicit accept shipped here means a web recipient who *replies* is no longer stuck, but declining,
  and accepting without replying, still have no web UI. Backlogged in `docs/03-roadmap/ROADMAP.md`.
* **Part 4 (shorter access TTL) is held** until web refreshes on 401.
