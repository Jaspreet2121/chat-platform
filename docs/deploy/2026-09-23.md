**`shared_infra` changed** (`8c74754`, `ddd180e`, `b93c277`). Every release statically embeds it, so

why the build step below names all of them.

Two ordering rules this deploy is bound by:

* **The migration goes first.** 129 and 130 add what the new code reads.
* **Gateway ships with-or-before auth, never auth alone.** Auth returns `:refresh_expired` and
  `:refresh_reused` as strings that `InternalApi.decode_result/2` rehydrates with
  `String.to_existing_atom/1`. A gateway that has not been rebuilt does not have those atoms, decodes
  them as raw strings, misses every clause, and answers **400 instead of 401** on refresh. The single
  `up -d` below satisfies this by bringing them up together.

The same wire applies to the implicit accept's `request_accepted` flag, but it degrades safely in both
directions (unknown atom → string → `nil` → no frame), so it does not constrain the order.

## 6. AASA — validate, then reload Caddy

> **ONE-TIME: the Caddy mounts change in this deploy, so Caddy is recreated ONCE here.** Every deploy
> after this one is validate + reload again, and this recreate is what makes that trustworthy.
>
> **Why.** `docker-compose.prod.yml` previously bind-mounted `Caddyfile` and `assetlinks.json` as
> SINGLE FILES. A single-file bind mount pins the file's **inode** at container start. `git pull`
> replaces a file by writing a new one and renaming over it, which changes the inode — so the
> container goes on reading the old file, or loses the path entirely, and **`caddy reload` reports
> success while reloading the previous config**. That happened on 2026-09-23. It is silent: validate
> passes, reload passes, and the served bytes never change.
>
> The fix is to mount the **directories** (`./infra/caddy:/etc/caddy:ro` and
> `./infra/caddy/srv:/srv:ro`), so every read goes through a fresh directory lookup and a pulled file
> is the file Caddy sees. `assetlinks.json` moved to `infra/caddy/srv/.well-known/` — it had the same
> latent bug, and `srv` is a separate directory from the config on purpose: everything under it is
> publicly served, so the Caddyfile must not be reachable from it. The Caddyfile's `root * /srv` is
> unchanged.

**Validate first.** A bad Caddyfile taken live restart-loops Caddy, and api, web and media all proxy
through it — that is the whole site, not one endpoint. Validate against the file on **disk**, not
through the old container, since the old container is exactly what cannot see the pulled file:

```bash
docker run --rm -v "$PWD/infra/caddy:/etc/caddy:ro" caddy:2.8-alpine \
  caddy validate --config /etc/caddy/Caddyfile
```

Expect `Valid configuration`. **If it does not say that, stop here** and change nothing — the running
Caddy is unaffected and the site stays up.

**Then the one-time recreate**, which picks up the new mounts:

```bash
docker compose -f docker-compose.prod.yml up -d caddy
docker compose -f docker-compose.prod.yml ps caddy --format '{{.Service}}\t{{.Status}}'
```

Caddy must read `Up …`, **not** `Restarting`.

**Prove the container is now reading the pulled files** — this is the check that would have caught
the 2026-09-23 failure, and it is the reason for the recreate:

```bash
docker compose -f docker-compose.prod.yml exec -T caddy \
  md5sum /etc/caddy/Caddyfile /srv/.well-known/assetlinks.json
md5sum infra/caddy/Caddyfile infra/caddy/srv/.well-known/assetlinks.json
```

The two pairs of hashes must match. **If they do not, the container is serving stale files** — do not
proceed, and do not trust any reload until they agree.

From here on, a Caddyfile change is validate + reload with no recreate:

```bash
docker compose -f docker-compose.prod.yml exec -T caddy \
  caddy validate --config /etc/caddy/Caddyfile
docker compose -f docker-compose.prod.yml exec -T caddy \
  caddy reload --config /etc/caddy/Caddyfile
```

**Shows it worked** — and this is also live check 3. **Read the body, not just the status code:**

```bash
curl -sS -D- https://web.growblic.com/.well-known/apple-app-site-association \
  | grep -iE "^HTTP/|^content-type|^content-length|^location"
echo "--- body ---"
curl -sS https://web.growblic.com/.well-known/apple-app-site-association | python3 -m json.tool
```

All four must hold:

* `HTTP/2 200` — **not** 301 or 302. iOS does not follow redirects for this file.
* `content-type: application/json`. Without the `header Content-Type` line this is `text/plain` and
  iOS rejects the file.
* **`content-length: 118`, not 0.** This is the one that has actually bitten: an earlier `respond`
  here used a backtick-quoted body that did not survive Caddyfile parsing and served **200 with an
  empty body** — healthy-looking and completely broken. `caddy validate` does not catch it.
* `python3 -m json.tool` parses it and it contains `FXGBWKT8FB.com.growblic.exway` with `/call/*` and
  `/join/*`. If the body were empty, this command errors — which is the point of using it.

Confirm Android did not regress — it moved directory in this deploy, so this is not a formality:

```bash
curl -sS -o /dev/null -w '%{http_code} %{content_type} %{size_download}\n' \
  https://web.growblic.com/.well-known/assetlinks.json
```

Expect `200 application/json` and a non-zero size.

And confirm the other hosts, since a reload affects everything Caddy fronts:

```bash
for h in api.growblic.com web.growblic.com media.growblic.com; do
  printf '%-22s %s\n' "$h" "$(curl -s -o /dev/null -w '%{http_code}' https://$h/health 2>/dev/null || echo ERR)"
done
```

> **Two things to know about the AASA.** It is served from **web.growblic.com** only, because
> `growblic.com` is a `redir` block and a redirect breaks universal links. The iOS app's Associated
> Domains entitlement must therefore read `applinks:web.growblic.com` — if it names the apex or
> `www`, the link silently falls back to Safari and nothing is logged server-side. And **`/join/*`
> has no web route yet** (`apps/web/src/app` has `call/[linkId]` and `invite/[code]`, no `join`): the
> path is claimed for the app, but a user without the app installed gets a 404 instead of a landing
> page. Worth a route in the web slice.

### 7.2 The refresh grace window

The claim: replaying a **just-rotated** refresh token inside 30 s returns a fresh pair; outside it
returns `auth.refresh_reused`. Both halves on account A only.

> **`device_id` is REQUIRED on every refresh, and the gateway does not tell you that.** The gateway's
> `require_fields` on this route checks only `refresh_token`, so a request without `device_id` is
> accepted and forwarded; auth then compares the submitted device against the one stored on the token
> (`AuthService.Tokens.valid_device?/2`), gets `nil` vs the real id, and answers **401
> `auth.refresh_invalid`**. That reads exactly like a broken grace window and is not one. It must be
> the SAME `device_id` used at login — `deploy-check-2026-09-23` in 7.1.

```bash
DEV=deploy-check-2026-09-23
R1=$(echo "$LOGIN" | python3 -c 'import json,sys;print(json.load(sys.stdin)["refresh_token"])')

# Rotate once. R1 is now the "just-rotated" token.
curl -sS -X POST $API/api/v1/auth/refresh -H 'content-type: application/json' \
  -d "{\"refresh_token\":\"$R1\",\"device_id\":\"$DEV\"}" | head -c 200; echo

# INSIDE the window: replay R1 immediately.
echo "--- inside 30s, expect 200 + a token pair ---"
curl -sS -o /tmp/inside -w '%{http_code}\n' -X POST $API/api/v1/auth/refresh \
  -H 'content-type: application/json' \
  -d "{\"refresh_token\":\"$R1\",\"device_id\":\"$DEV\"}"
head -c 200 /tmp/inside; echo
```

Expect **200** and a body with `access_token`.

```bash
# OUTSIDE the window: same token, after the 30s grace has passed.
sleep 35
echo "--- outside 30s, expect 401 auth.refresh_reused ---"
curl -sS -o /tmp/outside -w '%{http_code}\n' -X POST $API/api/v1/auth/refresh \
  -H 'content-type: application/json' \
  -d "{\"refresh_token\":\"$R1\",\"device_id\":\"$DEV\"}"
cat /tmp/outside; echo
```

Expect **401** and `"code":"auth.refresh_reused"`.

Reading the failures apart:

* **401 `auth.refresh_invalid` on all three** — `device_id` is missing or does not match the login.
  See the note above. This is not a grace-window failure.
* **400 instead of 401** — the gateway/auth atom mismatch described at the top: the gateway image was
  not rebuilt. Re-run steps 4 and 5 for `gateway`.
* **401 `auth.refresh_reused` on the INSIDE replay** — the grace window genuinely is not working, or
  `AUTH_REFRESH_GRACE_SECONDS` is set to `0` in `.env`. It is unset by default and defaults to 30.

> **Account deletion is deliberately not checked here.** Use `+15550199004` (fixed OTP `900004`),
> which exists for exactly this and is reusable: deletion NULLs the phone and the unique index is
> partial, so the number re-registers immediately. Never run it against a reviewer account or a real
> one. Note the username is held for 30 days, so pick a different handle on each run. Do it
> separately from this runbook — see `docs/09-devops/REVIEWER_LOGIN.md`.

## Rollback

The dump from step 2 is the only thing that undoes the migrations. Roll back in the reverse order of
the deploy.

**Code only** (the common case — the new images misbehave but the schema is fine). Both 129 and 130
are additive, so the previous images run happily against the new schema:

```bash
cd ~/chat-platform
git log --oneline -12                       # pick the last known-good SHA
git checkout <LAST_GOOD_SHA>
export GIT_SHA=$(git rev-parse --short HEAD)   # deliberately re-derived: this is the ROLLBACK commit, not $EXPECTED
docker compose -f docker-compose.prod.yml --profile kafka build \
  gateway auth conversation user message media notification

  gateway auth conversation user message media notification

```

**Caddy only** (the AASA is wrong, or the site misbehaves after step 6). Restore the file, validate,
reload — no recreate, because the directory mount from step 6 means the container sees the restored
file immediately:

```bash
git checkout <LAST_GOOD_SHA> -- infra/caddy/

# PROVE the container sees the restored file before reloading it. Skipping this is the exact
# 2026-09-23 failure: reload succeeds and silently keeps the config you are trying to roll back.
docker compose -f docker-compose.prod.yml exec -T caddy md5sum /etc/caddy/Caddyfile
md5sum infra/caddy/Caddyfile

docker compose -f docker-compose.prod.yml exec -T caddy \
  caddy validate --config /etc/caddy/Caddyfile
docker compose -f docker-compose.prod.yml exec -T caddy \
  caddy reload --config /etc/caddy/Caddyfile
curl -s -o /dev/null -w '%{http_code}\n' https://api.growblic.com/health
docker compose -f docker-compose.prod.yml ps caddy --format '{{.Service}}\t{{.Status}}'
```

**If the two md5sums differ**, the container is on stale files — it predates the step-6 recreate, or
was started from an older compose file. Recreate it once and re-check:
`docker compose -f docker-compose.prod.yml up -d caddy`.

**If Caddy is already restart-looping** it cannot be `exec`-ed into, so validate and reload are both
unavailable. Restore the file on disk and let the container pick it up:

```bash
git checkout <LAST_GOOD_SHA> -- infra/caddy/
docker compose -f docker-compose.prod.yml restart caddy
docker compose -f docker-compose.prod.yml logs --tail=30 caddy
```

**Full restore, including the schema** — last resort. This **destroys every row written since the
dump**, so take a second dump of the current state first or you lose the evidence of what went wrong.
And note it restores **Postgres only**: Scylla is untouched, so message rows survive while the
conversations and participants they reference are rolled back to the dump. Read *Follow-up 1* before
choosing this path:

```bash

gunzip -c ~/predeploy-2026-09-23.sql.gz | \
  docker compose -f docker-compose.prod.yml exec -T postgres \
```

## Follow-up 1 — Scylla has no backup

**The gap.** `pg_dump` in step 2 covers Postgres only. Messages are **Scylla-authoritative** in prod
(`MESSAGE_STORE_ADAPTER=scylla`), so the Postgres `messages` table is frozen and empty. The predeploy
dump therefore does not contain a single message, and the "full restore" rollback would bring back
accounts and conversations with **no message history at all**. Nothing currently backs up the
`scylla_data` volume.

Scope: keyspace `chat_messages`, tables `messages_by_conversation`, `message_receipts_by_conversation`,
`message_reactions_by_message`, `messages_by_user_inbox`, `messages_by_media`, `media_by_conversation`.
Single node, `--smp 1`, `--developer-mode 1`, volume `scylla_data`.

**Plan — `nodetool snapshot`, not a volume tar.** A snapshot flushes memtables and hardlinks the
SSTables, so it is consistent, near-instant and costs almost no disk at the moment it is taken. A
volume tar of a running Scylla is not consistent, and stopping Scylla to tar it means messaging is
down for the duration.

```bash
# 1. Snapshot (flushes first; hardlinks, so this is fast and cheap)
TAG=predeploy-$(date +%F)
docker compose -f docker-compose.prod.yml --profile scylla exec -T scylla   nodetool snapshot -t "$TAG" chat_messages

# 2. Schema — SSTables are useless without it
docker compose -f docker-compose.prod.yml --profile scylla exec -T scylla   cqlsh -e "DESCRIBE KEYSPACE chat_messages" > ~/scylla-schema-$TAG.cql

# 3. Copy the snapshot off the volume, then off the box
docker compose -f docker-compose.prod.yml --profile scylla exec -T scylla   tar -czf - -C /var/lib/scylla/data $(...paths of the snapshot dirs...) > ~/scylla-$TAG.tar.gz

# 4. Release the hardlinks, or they pin deleted SSTables and the disk grows
docker compose -f docker-compose.prod.yml --profile scylla exec -T scylla   nodetool clearsnapshot -t "$TAG" chat_messages
```

Step 3 needs the snapshot directory paths resolved (they are
`<keyspace>/<table>-<uuid>/snapshots/<tag>/`) — **that resolution is the part to work out and test
before relying on this**, which is why this is a plan and not a verified procedure.

Open questions to settle when building it: where the archive goes (S3, or the same place `pg_dump`
output should be going — neither is off-box today, which is its own gap); retention; whether restore is
`sstableloader` or a stop-and-copy into the data directory; and whether to run it on a schedule rather
than only before a deploy. **Restore must be tested at least once against a throwaway keyspace** — an
untested backup is not a backup.

Until this exists, **step 2's dump is not a full rollback point**, and the "full restore, including the
schema" section below carries that caveat.

## Follow-up 2 — the box wants a reboot

The host reports `System restart required` (a kernel or libc update landed via unattended-upgrades).
This is not urgent but should not drift: the running kernel keeps the unpatched code until a reboot.

**Plan — a scheduled maintenance window, not an opportunistic reboot.**

Before:

* take the Postgres dump **and** the Scylla snapshot above — a reboot is precisely when an unclean
  shutdown can cost data;
* `uptime`, and `cat /var/run/reboot-required.pkgs` to record what is pending and why;
* confirm restart policies will actually bring everything back. All 11 services are
  `restart: unless-stopped`, and **profiles do not affect this** — profiles are a compose-CLI concept,
  while the restart policy belongs to the container, so `scylla`, `kafka` and `notification` come back
  on their own. Verify rather than assume.

The real risk to plan around: **there is no `stop_grace_period` anywhere in the compose file**, so
every container gets Docker's default 10 seconds before `SIGKILL`. That is thin for Postgres, Scylla
and Kafka — an ungraceful stop means commitlog/WAL replay on the way back up and, in the worst case,
corruption. Either raise `stop_grace_period` for those three first (a compose change, so a recreate —
worth folding into the same window), or stop them explicitly with a longer timeout before rebooting:

```bash
docker compose -f docker-compose.prod.yml --profile kafka --profile scylla --profile calls   stop --timeout 60
sudo reboot
```

After: all containers `Up`, `/health` 200, and re-run the step 6 and step 7 checks. Raising
`stop_grace_period` permanently is the better fix, since an unplanned reboot gets no such courtesy.
